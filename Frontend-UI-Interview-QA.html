Interview Q&A — Responsive UI

This part is the React dashboard: mobile and desktop layout, dark mode, filter, sort, temperature bar chart, and Comfort Index unit tests. The frontend does not calculate the comfort score.

Say this in 30 seconds

I built a React dashboard with Vite. It calls GET /api/weather through a Vite proxy to Spring Boot on port 8080. The UI shows rank, city, weather, temperature, and the backend score. On a wide screen I use a table. On a phone I use cards. CSS media query is 768px. Dark mode uses a data-theme attribute and localStorage. Filter and sort run in the browser with useMemo. I removed sort by rank because it is the same order as sort by score. The chart is one bar per city for current temperature. I also wrote JUnit tests for ComfortCalculator.

Quick facts

  • Frontend: http://localhost:5173
  • Backend: http://localhost:8080
  • fetch("/api/weather") — Vite proxy to Spring Boot
  • Score and rank come from the backend only
  • Desktop table / mobile cards at 768px
  • Dark mode: data-theme + localStorage
  • Sort: score, temperature, name
  • Chart: bar height from each city temperature
  • Tests: mvn test — ComfortCalculatorTest

Product questions

Q1. What did you build in this step?

A. A responsive weather dashboard. It lists cities from my API. It works on phone and desktop. Bonus: dark mode, filter, sort, a temperature bar chart, and unit tests for the comfort formula.

Q2. Does the frontend calculate Comfort Index?

A. No. The backend already sends score and rank. React only shows them. If I calculated the score in React, someone could change it in the browser.

Q3. How is it responsive?

A. I use a CSS media query. Below 768px I show cards. At 768px and above I show a table. The page also uses a max width and flexible toolbar so inputs wrap on a small screen.

Q4. Why remove sort by rank?

A. Rank is made from score on the server. Highest score is rank 1. Sorting by rank and by score gave the same list. I kept sort by score.

Q5. How does filter work?

A. The user types a city or country. I keep the original API list. I filter a copy with includes() on name and country. I do not call the backend again.

Q6. How does the temperature chart work?

A. Each city is one bar. Bar height = abs(temperature) / maxAbsTemperature * 140px. I use absolute value so a negative temperature still has a bar. The city name is under the bar. Filter and sort also change the chart.

Technical questions

Q7. What is Vite and why a proxy?

A. Vite is the dev server for React. The UI runs on 5173. The API runs on 8080. The browser blocks a page on 5173 from calling 8080 (CORS) unless the server allows it. I set vite.config.js proxy: /api goes to http://localhost:8080. So fetch("/api/weather") stays same-origin on 5173, and Vite forwards it. I also added CorsConfig on Spring Boot for 5173 as a backup.

Q8. What is CORS?

A. Cross-Origin Resource Sharing. The browser treats different port as a different origin. localhost:5173 and localhost:8080 are different origins. Without CORS or a proxy, fetch fails.

Q9. Explain useState and useEffect in your App.

A. useState holds theme, data, error, loading, query, and sortBy. One useEffect writes theme to document.documentElement and localStorage. Another useEffect runs once ([]), fetches weather, then sets data or error. I use an ignore flag in cleanup so a slow response does not update state after unmount.

Q10. Why useMemo for the city list?

A. Filter and sort run only when data, query, or sortBy change. I copy the array first ([...data.cities]) so I do not mutate the API payload. Mutating the original array would break React state.

Q11. How does dark mode work technically?

A. I set data-theme="dark" or "light" on the html element. CSS variables in :root and [data-theme="dark"] change colors. localStorage remembers the choice after refresh. That is CSS custom properties, not a second website.

Q12. What is a media query?

A. CSS that applies only at a screen size. I hide the table on small screens (.desktop-only { display: none }) and show it from 768px. Cards are the opposite.

Q13. Why fetch, not Axios?

A. fetch is built into the browser. One GET is enough. I check res.ok and read JSON error from the backend.

Q14. What happens if the backend is down?

A. fetch fails or Vite proxy says connection refused. I show an error: start Spring Boot on port 8080.

Q15. Why Cache-Control no-store on the API?

A. So the browser does not keep an old /api/weather JSON. Server cache is our 5-minute Map. Browser cache is different.

Q16. Could you sort on the backend instead?

A. Yes, with query params. I sort on the frontend because the assignment bonus is frontend sorting, and the list is only 8 cities. The default rank order still comes from the server.

Q17. How do you test Comfort Index?

A. JUnit 5 in ComfortCalculatorTest. I call calculate() with known numbers. Ideal 22°C, 50% humidity, 0 wind should be 100. Colombo-like numbers should be mid, not 100. Null temperature: temp part is 0, so score is 0.5*0 + 0.3*100 + 0.2*100 = 50. Extreme weather clamps to 0. I run mvn test. These tests do not start the web server.

Q18. What is a unit test vs an API test?

A. A unit test checks one class, ComfortCalculator, with no OpenWeatherMap. An API test would call GET /api/weather. I unit-tested the formula because the assignment asked for tests on the Comfort Index function.

Q19. Why is ComfortCalculator a @Component?

A. Spring can inject it into WeatherService. In the test I do new ComfortCalculator() myself. I do not need the full Spring context for these tests.

Q20. What is the SPA here?

A. Single Page Application. One HTML page, React updates the DOM. No login page yet. Auth0 would be a later step.

Q21. How would you improve the chart?

A. I could use a library like Recharts, add axes, or show history if the backend stored old temperatures. Right now I only have current weather, so one bar per city is honest.

Q22. What have you not built yet?

A. Auth0 login, MFA, and protecting the dashboard. The UI is public if someone opens 5173.
