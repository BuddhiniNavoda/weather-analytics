Interview Q&A — Server cache

Practice for the cache I coded: 5 minutes on the backend, raw weather, processed list, HIT and MISS. Simple answers. Cache is not the same as cash.

Say this in 30 seconds

I cache weather on the server for 5 minutes. I save two things: raw OpenWeatherMap JSON per city, and the full ranked list with scores. If the list is still fresh, I return it and do not call OpenWeatherMap. That is a HIT. If it is empty or older than 5 minutes, that is a MISS. I rebuild, save, and return. GET /api/cache/status shows HIT or MISS. The cache is in memory, so it is gone when I restart the app.

Quick facts

  • GET http://localhost:8080/api/weather
  • GET http://localhost:8080/api/cache/status
  • TTL = 300 seconds (5 minutes)
  • WeatherCache is a Map in memory
  • Processed cache = ranked list with score
  • Raw cache = OpenWeatherMap JSON per city ID
  • HIT = data younger than 5 minutes
  • MISS = no data, or older than 5 minutes

Q1. What is a cache in your project?

A. It is saved weather on the server. I keep it for 5 minutes so I do not call OpenWeatherMap on every refresh.

Q2. Why do you cache?

A. OpenWeatherMap has limits. Eight cities on every click is many calls. Cache is faster. Weather does not change every second. The assignment also asks for 5 minutes and a HIT/MISS debug URL.

Q3. Is this cache in the browser?

A. No. It is on the Spring Boot server. The browser only asks my API. I also send Cache-Control no-store so the browser does not keep an old JSON page.

Q4. What is raw cache vs processed cache?

A. Raw is the OpenWeatherMap JSON for one city, keyed by city ID. Processed is my full API list after comfort score and rank. Processed is the one I check first. If it is a HIT, I skip OpenWeatherMap and skip the formula.

Q5. Why both?

A. Raw protects the weather API per city. Processed makes the whole page fast. The assignment says raw is required and processed is preferred. I did both.

Q6. Walk me through GET /api/weather with cache.

A. WeatherService asks WeatherCache for the processed list. If it is fresh, return it (HIT). If not, for each city I try raw cache. HIT uses saved JSON. MISS calls OpenWeatherMap and saves raw. Then I calculate scores, sort, set rank, save the processed list, and return.

Q7. What is HIT?

A. I already have data and it is less than 5 minutes old. I use it. I do not call OpenWeatherMap for that part.

Q8. What is MISS?

A. There is nothing saved, or it is older than 5 minutes. I fetch or rebuild, then save.

Q9. How do you know it is still fresh?

A. Each cache entry has savedAt. Age = now minus savedAt. If age is less than 300 seconds, it is fresh. cache.ttl-seconds in application.properties is 300.

Q10. Where is this in the code?

A. WeatherCache holds the maps. CacheEntry has data and savedAt. WeatherService uses the cache. CacheStatusService builds the debug JSON. WeatherController has GET /api/cache/status next to GET /api/weather.

Q11. How do you show HIT and MISS?

A. GET http://localhost:8080/api/cache/status. lastWeatherRequest is from the last weather call. processed and raw show what is in memory now, with ageSeconds.

Q12. How do you test it?

A. Restart the app so memory is empty. Call /api/weather then /api/cache/status. processed should be MISS. Call /api/weather again. Then status should show HIT. Wait 5 minutes, call weather again, MISS. fetchedAt stays the same on a HIT.

Q13. Why did /api/cache/status give 404 before?

A. The running app was started before that URL existed. Spring 404 means no mapping. I had to stop Java and run mvn spring-boot:run again.

Q14. What happens if you restart the server?

A. The cache is empty. It is only in RAM. That is a trade-off. Redis would keep data after restart, but I do not need Redis for this task.

Q15. If you change the comfort formula, what should you do?

A. Restart the app. If I do not, the processed cache can keep old scores and ranks for up to 5 minutes.

Q16. Why ConcurrentHashMap?

A. More than one request can hit the API at the same time. ConcurrentHashMap is safer than a normal HashMap for that. For this small app a simple Map would often work too.

Q17. Does cache change the Comfort Index formula?

A. No. On a MISS I still use ComfortCalculator the same way. On a HIT I return the list I already scored.

Q18. Why can weather numbers look the same even without cache?

A. OpenWeatherMap current weather often stays the same for many minutes. Cache is still useful because I skip extra HTTP calls. fetchedAt changing vs not changing helps me see HIT vs a new build.

Q19. What is TTL?

A. Time to live. How long we keep data. Mine is 5 minutes. After that, next request is a MISS.

Q20. Trade-offs?

A. Good: fewer API calls, faster, I can show HIT/MISS. Bad: data can be up to 5 minutes old, restart clears cache, formula changes wait until cache dies unless I restart.

Q21. Would you use Redis?

A. Later, if I run more than one server or I need cache after restart. For one local app, in-memory is enough and easier to explain.

Q22. Does the frontend calculate cache?

A. No. Cache is server-side only, like the comfort score.

If you get stuck

Draw HIT vs MISS on paper. Point to WeatherCache. Say 5 minutes, in memory, two caches, /api/cache/status. Do not say Redis if it is not in the project.
