Interview Q&A — Comfort Index

Practice for the part I coded: live weather on the backend, then Comfort Index and rank. Use simple answers. If they ask about cache, login, or UI, I say I have not built that yet.

Say this in 30 seconds

I built a Spring Boot API. It reads city IDs from a JSON file and gets live weather from OpenWeatherMap on the server. Then the backend calculates a Comfort Index from 0 to 100 using temperature, humidity, and wind. Cities are sorted by that score. Rank 1 is the most comfortable. The browser does not calculate the score.

Quick facts

  • GET http://localhost:8080/api/weather
  • Score is made in ComfortCalculator on the backend
  • tempScore = 100 − |temperature − 22| × 5
  • humidityScore = 100 − |humidity − 50| × 1.5
  • windScore = 100 − windSpeed × 10
  • score = 0.50×temp + 0.30×humidity + 0.20×wind
  • Then sort high to low and set rank

Q1. What did you add in this part?

A. After live weather, I added a Comfort Index on the server. Each city gets a score from 0 to 100 and a rank. Rank 1 is the best. The formula is in ComfortCalculator. WeatherService calls it, then sorts the list.

Q2. What is the Comfort Index?

A. It is a number from 0 to 100. 100 means very nice outdoors. 0 means very bad. It is my own rule to compare cities. It is not a medical test.

Q3. Why must the backend calculate the score?

A. If the frontend calculates it, anyone can change the formula in the browser. Then ranks would not be trusted. One formula on the server means every user sees the same rank. The assignment also says the backend must compute the score.

Q4. Walk me through one request.

A. WeatherController gets GET /api/weather. WeatherService reads city IDs from cities.json. It calls OpenWeatherMap for each city. ComfortCalculator makes the score from temperature, humidity, and wind. Then we sort by score, highest first, and set rank 1, 2, 3. The JSON includes score and rank.

Q5. Which weather numbers do you use?

A. Temperature in Celsius, humidity in percent, wind speed in metres per second. All from OpenWeatherMap. I do not use Temp or Status from cities.json. That file is only for CityCode.

Q6. Why not add temperature + humidity + wind as they are?

A. The units are different. Humidity is around 70. Wind is around 5. Humidity would always win. So I first turn each one into a 0–100 score, then mix them with weights.

Q7. Explain the temperature formula.

A. tempScore = 100 − |temperature − 22| × 5. I treat 22°C as nice weather. The bars mean hot and cold both lose points. × 5 means each 1°C away from 22 loses 5 marks. If I only subtract the gap, 30°C would still look like about 91, which is too good. Then I keep the result between 0 and 100.

Q8. Why 22°C?

A. It is my default for mild outdoor weather so I can compare all cities on one scale. It is a choice. Someone in Colombo may feel fine at 30°C. I can say that in the interview.

Q9. Explain the humidity formula.

A. humidityScore = 100 − |humidity − 50| × 1.5. 50% is my ideal. Too dry and too sticky both lose points. I use 1.5, not 5, because humidity already goes from 0 to 100. If I used × 5, 74% humidity would hit 0 too fast.

Q10. Explain the wind formula.

A. windScore = 100 − windSpeed × 10. More wind means a lower score. Calm wind is 100. × 10 is needed because wind is a small number like 1 to 6. Without × 10, wind would almost not change the rank. 10 m/s wind would be score 0.

Q11. Why no absolute value on wind?

A. In version 1 I say more wind is worse. I do not say 2 m/s is ideal and 0 m/s is also bad. That keeps it simple. Later I can say a little wind is nice when it is hot.

Q12. Why weights 0.50, 0.30, 0.20?

A. They add to 1. Temperature is 50% because heat and cold are what people feel first. Humidity is 30%. Wind is 20% as a small extra. I can change these numbers live if they ask.

Q13. Show the full formula.

A. score = 0.50 × tempScore + 0.30 × humidityScore + 0.20 × windScore. Then clamp 0 to 100 and round to 2 decimals.

Q14. Calculate Colombo quickly. 30.58°C, 74%, 5.84 m/s.

A. Temp gap = 8.58. tempScore = 100 − 8.58×5 ≈ 57. Humidity gap = 24. humidityScore = 100 − 24×1.5 = 64. windScore = 100 − 5.84×10 ≈ 42. Final ≈ 0.5×57 + 0.3×64 + 0.2×42 ≈ 56. So Colombo is mid, not rank 1. It is hot and humid.

Q15. Why might Boston rank higher than Colombo?

A. Boston is closer to 22°C and the wind is weaker. Colombo is about 30°C and more humid. With my formula, milder and calmer cities get a higher score.

Q16. Where is this in the code?

A. ComfortCalculator has the math. WeatherService gets weather, calls calculate, sorts by score, then setRank. CityWeather has score and rank fields. The controller only returns the JSON.

Q17. What is clamp?

A. If the number is below 0 I use 0. If it is above 100 I use 100. So a very hot city cannot get a negative score.

Q18. What if temperature is missing?

A. In my code, null temperature or humidity gives that sub-score 0. Null wind I treat as 0 m/s, so wind score is 100. Normally OpenWeatherMap sends all three.

Q19. How do you rank?

A. After every city has a score, I sort highest score first. First city gets rank 1, next rank 2. The API list is already in rank order.

Q20. If two cities have the same score?

A. Java sort keeps a stable order, so they keep their old order. I did not add a special tie-break. I can say I would use city name next if needed.

Q21. Why can temperature look the same when I refresh?

A. OpenWeatherMap current weather does not change every second. fetchedAt should change. That means I called the API again. The weather numbers can stay the same for about 10 minutes.

Q22. If they ask you to add one more parameter live, what do you do?

A. I already have clouds. I can add cloudScore = 100 − clouds. Then change weights to add to 1, for example 0.40, 0.25, 0.20, 0.15. I change ComfortCalculator, save, refresh, and show if ranks move. I talk while I type.

Q23. What is a trade-off of your formula?

A. It is simple, not perfect. 22°C is my choice. Wind always lowers the score, even a small breeze. I made it easy to explain and easy to change.

Q24. Why Spring Boot layers?

A. Controller is HTTP. Service is the flow. ComfortCalculator is only the formula. Repository talks to the file and OpenWeatherMap. DTO is the JSON. If they ask to change the formula, I only edit ComfortCalculator.

Q25. What have you not built yet?

A. No 5-minute cache. No Auth0 login. No frontend dashboard. I would do cache next, then a simple UI, then Auth0.

Q26. How do you hide the API key?

A. The key is in application-local.properties. That file is gitignored. The frontend never sees the key.
